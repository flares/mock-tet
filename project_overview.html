What is this project?

A static site on GitHub Pages that serves CTET Paper 2 (Classes VI–VIII, Mathematics & Science stream) candidates. Two distinct interfaces: a mobile-first installable PWA question browser (primary focus) and a CBT mock-test replica of the NTA exam interface (secondary).

What happens when a user visits the PWA

First visit — cold start (no Service Worker installed)

Network requests in order

qb_pwa.html→ r2-explanations.js→ explanation.js→ firebase-ai.js→ firebase-config.js
exams/qb_index.json (2.6 MB)→ 3,150 questions in memory
Worker GET /index→ ✨ count (questions with explanations)
Worker GET /images/CDP/…/sprite.png→ canvas split → Q1 displayed
Prefetch Q2, Q3 sprites(background)

Service Worker registers and installs during this visit. Pre-caches 7 shell files (see below). Does not serve anything until next visit.

Subsequent visits — warm start (Service Worker active)
qb_pwa.html→ SW cache-first → instant (no network)
qb_index.json→ SW stale-while-revalidate → served from cache immediately+ background ETag check → updates if changed
sprite PNGs→ SW cache-first → instant after first browse( 1-year immutable)
exam JSONs (real-*.json)→ SW network-first → live if online, falls back to cache if offline

If qb_index.json changed in background: "App update available — Reload" banner appears. If SW itself updated: "App updated" toast fires on controllerchange.

Background sync (Android Chrome only)
  • Background Sync API: when device comes back online after being offline, SW fires sync event → re-validates qb_index.json via ETag.
  • Periodic Background Sync: registered on Android Chrome with tag qb-refresh — SW wakes periodically (every ~24h) to silently revalidate the question index even when app is not open.
  • iOS PWA limitation: neither Background Sync nor Periodic Sync are supported. The visibilitychange and pageshow handlers (bfcache fix) trigger re-init when the user returns to the app.

1 — PWA startup flow

User opens qb_pwa.html
Check localStorage cache_bust_v→ if mismatch: wipe qb_index_cache_v1 + ai_exp_persist:* keys
Read qb_index_cache_v1 from localStorage→ if valid: render immediately (warm)
fetch qb_index.json (via SW stale-while-revalidate)→ if newer: update localStorage cache + show update banner
applyFilters()→ renderCurrent()→ _loadSpritePieces(item)
R2 Worker GET /index→ populate _indexSet → ✨ counter

2 — Sprite rendering

Each question in qb_index.json has a spriteUrl and sprite coords object. Instead of loading 5 separate images (question + 4 options), only 1 sprite PNG is fetched and split on a canvas.

item.spriteUrl + item.sprite
new Image(); img.crossOrigin = 'anonymous'→ img.src = spriteUrl→ SW / R2 Worker
img.onload→ for each key in sprite: canvas.drawImage(img, 0, y, w, h, 0, 0, w, h)
canvas.toDataURL() per piece→ _spriteCache.set(questionImage, pieces)
pieces.question → <img#pwa-qimg src>    pieces.option1–4 → option <img>

Fallback path: if spriteUrl absent or img.onerror fires → use original questionImage and optionImages paths from GitHub Pages (question_bank/**/*.png).

Sprite compression: 4-colour palette PNG (Pillow ADAPTIVE) + optipng -o2. Combined sprite is typically 15–30% smaller than the sum of individual images.

3 — AI explanation load order

When the user taps "Explain with AI", the ExplanationModal tries sources in priority order:

1. localStorage ai_exp_persist:<folder>→instant display if cached (no network)
2. R2 via Worker GET /explanations/:subject/:folder→best explanation (highest likes−dislikes)
3. Generate via Gemini 2.5 Flash (Firebase AI SDK)→returns HTML string
POST to Worker → R2+POST /index to register questionId+cache in localStorage
4. "No explanation yet" message(if all above fail)

Like/Dislike: PATCH /explanations/…/:expId with action = like | unlike | dislike | undislike. New best explanation (highest net score, then most recent) shown on next open.

4 — Progress tracking

All progress is device-local (localStorage only). The PWA computes counts on every render from the in-memory sets.

Mark understood (FAB tap)→ add to understoodSet→ saveUnderstoodSet → localStorage→ updateHeaderProgress()
Mark for review (FAB tap)→ push to revisionList→ saveRevisionList → localStorage→ updateHeaderProgress()

Progress counter = questions where (questionImage in understoodSet) OR (questionImage in revisionList), scoped to current filter. Chip counts similarly scoped.

5 — CBT exam flow (exam.html)

index.html→ instructions.html (checkbox gate, init ExamState)→ exam.html
fetch exams/<id>.json→ ExamState.init(examData)→ ExamTimer.start(duration)
User navigates / answers / marks→ state updates → palette re-renders
Submit / time-up→ compute score per section→ write result to localStorage→ redirect to result.html

Pipeline A — New real-paper image data from coworker

Run all steps in order. Steps 2–5 must always run together; partial runs will leave the index out of sync with the exam JSONs.

Step 1 — Sync question_bank from coworker machine

rsync -av --delete "/mnt/c/Users/ymano/Universe/coworker/TET Preparation/question_bank/" /home/yadman/mock-tet/question_bank/

Copies question/option PNGs, metadata.json files, questions.json, index.csv from Windows via WSL. --delete removes anything no longer on source. Run on WSL.

Step 2 — Regenerate all real-paper exam JSONs

python3 scripts/build_real_exams.py

Reads question_bank/questions.json (single source of truth for answers) → writes/overwrites all 21 exams/real-*.json → updates exams/manifest.json. Must regenerate ALL every sync, not just new papers — if the coworker corrected an answer, the old exam JSON will silently diverge otherwise. Section order: CDP → Telugu → English → Mathematics → Science. Also calls build_qb_index.py at the end.

Step 3 — Build sprite PNGs (skip existing unless --force)

python3 scripts/build_sprites.py

For each question folder: stacks question.png + option1–4.png vertically into a single PNG. Converts to 4-colour palette (Pillow ADAPTIVE, same depth as source). Compresses with optipng -o2. Writes sprite.png and patches metadata.json with sprite coords. Skips folders with existing sprite.png. Use --subject CDP or --paper 2026-Jan-03-Shift1 to scope. Requires Pillow and optipng.

Step 4 — Upload sprites to R2 (requires wrangler login)

python3 scripts/upload_sprites.py

Calls wrangler r2 object put tet-questionbank-explanations/images/<Subject>/<folder>/sprite.png for every sprite.png. Runs 12 uploads in parallel via ThreadPoolExecutor. Use --subject CDP to scope; --dry-run to preview without uploading. wrangler binary is at worker/node_modules/.bin/wrangler; run from worker/ directory. Re-auth if needed: cd worker && npx wrangler login.

Step 5 — Rebuild the PWA question index

python3 scripts/build_qb_index.py

Reads all "type": "Real Paper" entries from manifest.json → flattens all questions → dedupes on questionImage → enriches each entry with spriteUrl and sprite coords from metadata.json → writes exams/qb_index.json. Already called automatically by step 2; re-run explicitly after step 3 if sprite coords changed.

Step 6 — Deploy Worker (only if worker/src/index.js changed)

cd worker && npx wrangler deploy

Pushes Worker code to Cloudflare. Required only on Worker code changes. Git push does NOT deploy the Worker. Currently pending: GET /images/ endpoint for sprite serving (added in last session, not yet live).

Step 7 — Commit & push to GitHub

git add exams/ question_bank/ qb_pwa.html scripts/ worker/ && git commit -m "..." && git push

GitHub Actions auto-deploys to Pages. Include: updated exam JSONs, qb_index.json, metadata.json files (with sprite coords), any HTML/JS changes. Do NOT include sprite.png files (they're gitignored and live in R2 only). Always update change_history.md and bump APP_VERSION in qb_pwa.html before committing.

How tests mock the app

  • manifest.json — intercepted; returns empty papers array.
  • Cloudflare Worker (**tet-qb-worker**) — intercepted by URL pattern. /images/ requests return a 1×1 blank PNG (so sprite canvas path is exercised, not just the error fallback). All other Worker requests return empty JSON.
  • question_bank/** — intercepted; returns a 1×1 blank PNG (fallback image path).
  • localStorage seeding — done via page.addInitScript() before page scripts run, so the app boots with pre-populated understood/revision data.
